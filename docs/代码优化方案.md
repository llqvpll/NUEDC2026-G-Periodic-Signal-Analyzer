## 1. 算法精度优化 (P0)

### 1.1 Hanning 窗值重复计算 → 预存窗表

**问题**: `GTI_FindPeaks()` 第244-245行每次 FFT 前都实时计算 4096 个 Hanning 窗值（4096 次 `cosf`），而 `GTI_WinInit()` 只算了窗函数和 `g_winsum`，窗值没有存表。`GTI_DtftAmp()` 也依赖 `g_xin[]`（已加窗），但窗值是隐含在 `g_xin` 里的。

**方案**:
```c
// 新增: 预存 Hanning 窗表
static float g_hann[GTI_N];  // +16KB CCM

// GTI_WinInit() 改为:
static void GTI_WinInit(void)
{
    u32 i;
    g_winsum = 0.0f;
    for (i = 0; i < GTI_N; i++) {
        g_hann[i] = 0.5f - 0.5f * cosf(2.0f * GTI_PI * (float)i / (float)(GTI_N - 1));
        g_winsum += g_hann[i];
    }
}

// GTI_FindPeaks() 中改为:
for (i = 0; i < GTI_N; i++)
    g_xin[i] = g_x[i] * g_hann[i];  // 查表替代 cosf
```

**收益**: 每次 FFT 省掉 4096 次 `cosf` 调用（约 2-3ms），自动刷新时效果明显。
**内存**: +16KB CCM（当前 CCM 约 57KB/64KB，需确认余量，可能需要把 `g_xout` 改用 `g_xin` 原地操作省 16KB）。

### 1.2 Item3 FIR 滤波 → CMSIS-DSP arm_fir_decimate_f32

**问题**: `GTI_Preprocess()` 第203-209行，Item3 的 FIR+抽取是纯 C 双重循环：127 阶 × 4096 输出 = 520,192 次浮点乘加。手动循环无法利用 CMSIS-DSP 的优化。

**方案**:
```c
#include "arm_math.h"

// 新增 CMSIS-DSP FIR+抽取实例
static arm_fir_decimate_instance_f32 g_fir_dec;
static float g_fir_state[GTI_N_RAW3 + GTI_FIR_TAPS - 1];  // 状态缓冲

// GTI_FirDesign() 中追加初始化:
arm_fir_decimate_init_f32(&g_fir_dec, GTI_FIR_TAPS, GTI_DECIM, 
                           g_fir, g_fir_state, GTI_N_RAW3);

// GTI_Preprocess() Item3 分支改为:
// 1. 整型转 float 并去均值
for (i = 0; i < GTI_N_RAW3; i++)
    g_xin_tmp[i] = (float)raw[i] - mean;  // 需要一个临时缓冲
// 2. 一次调用完成 FIR + 4倍抽取
arm_fir_decimate_f32(&g_fir_dec, g_xin_tmp, g_x, GTI_N_RAW3);
```

**收益**: CMSIS-DSP 的 `arm_fir_decimate_f32` 内部做了循环展开和 FPU 优化，实测比纯 C 快 2-3 倍。Item3 测量链路的 FIR 步骤从约 6ms 降到约 2ms。
**注意**: `arm_fir_decimate_f32` 会自动处理群延迟，`GTI_FIR_OFF` 偏移可以去掉。需要额外一个临时 float 缓冲（16528×4=64KB），放不下 CCM，需要放主 SRAM 或复用 `g_xout` 空间。

### 1.3 波形显示 GTI_FullFir 重复计算 → 预计算

**问题**: `GTI_ShowWave()` Item3 分支（第660-685行），对每个显示点都调用 `GTI_FullFir()`，每个点 127 次乘加。假设显示 500 个点，就是 63,500 次乘加——而且范围估算时还按 4 步抽稀再算一遍。更严重的是，`GTI_FullFir` 在第606行的索引 `raw[m + (GTI_FIR_TAPS-1)/2 - k]`，当 m 较小时会访问负索引（数组越界）。

**方案**:
```c
// 方案A: 在 GTI_Preprocess Item3 分支中，额外存一份波形显示用的抽取后数据
// g_x[] 本身就是 FIR+抽取后的结果（4096点@1.2MHz），可以直接用!
// GTI_ShowWave Item3 分支改为直接使用 g_x[]，不再调用 GTI_FullFir

// 方案B: 如果需要全速率(4.8MHz)波形，在预处理时一次性 FIR 全量数据
// 需要额外缓冲，但只算一次而非每点算一次
```

**收益**: 消除每次波形刷新的 63,500+ 次乘加，波形显示从约 10ms 降到 <1ms。同时修复数组越界 bug。
**推荐**: 方案A，直接复用 `g_x[]`（已经是 FIR 后的数据），波形从 1.2MHz 域取，完全够用（500kHz 信号在 1.2MHz 采样下每周期 2.4 点，虽然点少但可线性插值；如果要更密，可以按 2MHz 重新采集波形数据）。

### 1.4 GCD 搜索范围和容差优化

**问题**: `GTI_GcdF1()` 第299行 `k0 <= 16`，对于高次谐波（如 16 次以上）可能漏搜。第302行频率范围 `fc < 9000.0f || fc > 550000.0f` 是硬编码的，没有根据 Item 区分。

**方案**:
```c
// 根据 Item 调整搜索范围
float f_min = (G.item == 1) ? 9000.0f : 9000.0f;   // 都从 9kHz 起
float f_max = (G.item == 1) ? 205000.0f : 505000.0f; // Item1: 200k+5k, Item2/3: 500k+5k
int   k0_max = 20;  // 扩大到 20 次

// 容差改为自适应: 基频越低，bin 越宽，容差越大
float tol = 0.5f * bin;  // 从 0.35*bin 放宽到 0.5*bin（半个 bin）
```

**收益**: 高次谐波场景（题目说明3的例子：10.5k/31.5k/42k = 10.5kHz 基频 × 1/3/4）不会漏搜。

### 1.5 DTFT 幅值修正: 加窗补偿

**问题**: `GTI_DtftAmp()` 第358行 `return 2.0f * sqrtf(sr*sr + si*si) / g_winsum`，这个 `g_winsum` 是 Hanning 窗的相干增益（N/2），用于补偿加窗导致的幅度衰减。但这个公式只在频率恰好对齐 bin 时精确。当频率不对齐时（非整数 bin），Hanning 窗的幅度修正因子不是简单的 `1/WinSum`，而是需要考虑窗谱泄漏。

**当前状态**: 对于本项目的使用场景（谐波间隔 >= 20 bin，Hanning 旁瓣 -31dB），这个误差在 0.1% 级别，已经很好了。这个优化是锦上添花。

**方案**: 保持现状，但在注释中明确说明精度边界。如果后续实测发现特定频率点幅值偏差 >1%，再考虑加入插值修正。

## 2. 迪文屏数据缺失修复 (P0)

### 2.1 波形数据未发送到迪文屏

**问题**: `GTI_ShowWave()` 只在 SSD1963 上画波形，对迪文屏只调了 `DWIN_SwitchPage(1)`（第822行），没有调用 `DWIN_SendWavePoints()`。迪文屏波形页是空白的。

**方案**: 在 `GTI_ShowWave()` 的每个分支末尾，收集屏幕坐标对，调用 `DWIN_SendWavePoints()` 分批发送：
```c
// 在画线循环中收集坐标
u16 dwin_xy[240];  // 最多 120 点/帧
int dwin_cnt = 0;
// ... 画线循环中 ...
if (dwin_cnt < 120) {
    dwin_xy[dwin_cnt*2]   = (u16)xpix1;
    dwin_xy[dwin_cnt*2+1] = (u16)ypix1;
    dwin_cnt++;
}
// 循环结束后分批发送
DWIN_ClearGraph(DWIN_VP_GRAPH_WAVE);
DWIN_SendWavePoints(dwin_xy, dwin_cnt);
// 如果超过 120 点，第二批发送剩余点
```

**注意**: 当前 `DWIN_SendWavePoints` 单帧上限 120 点（缓冲 256B 限制），波形约 532 像素需要 5 批。需要改用大缓冲或实现分包发送。

### 2.2 频谱数据未发送到迪文屏

**问题**: `GTI_ShowSpec()` 同理，只切了页面 `DWIN_SwitchPage(2)`（第892行），没发送频谱柱状图数据。

**方案**: 在 `GTI_ShowSpec()` 末尾，将像素列的 `ytop` 值转换为柱高数组，调用 `DWIN_SendSpecBars()`：
```c
u16 bar_heights[30];  // 最多 30 柱
// 将 532 像素按 ~18px 宽度分 30 组，取每组最大值
// 发送
DWIN_SendSpecBars(bar_heights, 30, 15, 3);
```

### 2.3 DWIN_SendWavePoints 缓冲不足 → 扩大或分包

**问题**: `Drive_Dwin.c` 第16行 `static u8 s_buf[256]`，单帧最多容纳 120 个坐标点。但波形显示需要 532 个像素点。

**方案**: 
```c
// 方案A: 扩大缓冲到 1024B（可容纳 254 点/帧）
static u8 s_buf[1024];

// 方案B: 保持 256B 缓冲，在 DWIN_SendWavePoints 内部分包
void DWIN_SendWavePoints(const u16 *xy_pairs, u16 n_points)
{
    u16 sent = 0;
    while (sent < n_points) {
        u16 batch = n_points - sent;
        if (batch > 120) batch = 120;
        _send_wave_batch(&xy_pairs[sent * 2], batch);
        sent += batch;
    }
}
```

**推荐**: 方案B，不增加静态内存，逻辑更清晰。

## 3. 性能优化 (P1)

### 3.1 g_xout 复用 → 省省 16KB CCM

**问题**: `g_xin[4096]` 和 `g_xout[4096]` 各占 16KB CCM。`arm_rfft_fast_f32` 的输入输出可以原地操作（CMSIS-DSP 文档允许 `pInput == pOutput`）。

**方案**: 合并为一个缓冲，FFT 原地操作：
```c
// 删除 g_xout，FFT 原地
static float g_fft[GTI_N];  // 既做输入又做输出
arm_rfft_fast_f32(&g_rfft, g_fft, g_fft, 0);
```

**收益**: 省出 16KB CCM，为 1.1 节的 Hanning 窗表腾出空间。

### 3.2 自检兜底逻辑掩盖问题

**问题**: `GTI_Measure()` 第518-544行，自检模式下如果 `npk <= 0`（FFT 管线异常），直接注入已知结果而非报错。这会导致开发者以为自检通过了，但实际 FFT 可能有问题。

**方案**: 自检模式下 FFT 失败时显示明确的错误信息：
```c
if (npk <= 0)
{
    if (g_selftest) {
        G.valid = 0;
        GTI_Hint("自检失败:FFT异常");  // 明确报错
        return;
    }
    return;
}
```

### 3.3 自动刷新频率可调

**问题**: 主循环第1125行 `auto_cnt >= 100`（1秒刷新），不可配置。比赛时可能需要更快或更慢的刷新。

**方案**: 增加刷新间隔配置，用按键 [8]/[9] 或在代码中用宏控制：
```c
#define GTI_AUTO_INTERVAL_MS  1000  // 可改为 500/2000 等
if (auto_cnt >= GTI_AUTO_INTERVAL_MS / 10)
```

### 3.4 比较器等待优化

**问题**: `GTI_Measure()` 第578-584行，比较器测频最多等待 200ms（20×10ms）。如果信号幅度太小，比较器不触发，白白等 200ms。

**方案**: 先检查 ADC 数据幅度，太小就跳过比较器：
```c
// 在 GTI_Preprocess 后检查信号幅度
float signal_range = max(g_x) - min(g_x);  // 粗略估算
if (signal_range < 100.0f) {  // < 100 码 ≈ < 15mV，比较器可能不触发
    G.fref = 0.0f;
} else {
    G.fref = Get_Frequency();
    // ... 等待逻辑
}
```

## 4. 代码结构重构 (P1)

### 4.1 app_gti.c 1142 行 → 拆分 4 文件

**问题**: 单文件 1142 行，远超 300 行规范。测量引擎、界面显示、按键处理混在一起。

**方案**:

| 新文件 | 行数(估) | 内容 |
|--------|----------|------|
| `app_gti.c` | ~120 | 主入口 GTI_Run() + 主循环 |
| `app_gti_measure.c` | ~350 | GTI_Preprocess / GTI_FindPeaks / GTI_GcdF1 / GTI_DtftAmp / GTI_FirResp / GTI_TimeParams / GTI_Measure / GTI_SelfTestGen |
| `app_gti_display.c` | ~450 | GTI_DrawSkeleton / GTI_ShowParams / GTI_ShowWave / GTI_ShowSpec / GTI_ClearPlot / GTI_Hint |
| `app_gti_input.c` | ~80 | GTI_HandleKey |
| `app_gti.h` | ~80 | 公共接口 + GTI_State 结构体 + 配置常量 |

**注意**: `GTI_State G` 和所有缓冲需要通过 `app_gti_internal.h`（内部头文件）在 4 个文件间共享，不暴露给外部。

### 4.2 GTI_ShowWave 三分支代码重复 → 提取公共函数

**问题**: `GTI_ShowWave()` 有三个大分支（Item3: 644-694行 / 自检: 695-745行 / Item1-2: 746-817行），每个分支都做相同的事：找过零点 → 算范围 → 画线 → 画刻度。约 170 行重复逻辑。

**方案**: 提取公共绘图函数：
```c
// 统一波形绘制接口: 传入数据数组+起始+点数+每周期点数
static void GTI_DrawWaveform(const float *data, int start, int npts, 
                              float ppp, int periods, float fs_display);
```

三个分支只需准备数据，然后调用同一个绘图函数。预计从 170 行压缩到 80 行。

### 4.3 DWIN_SetMode switch-case → 数组循环

**问题**: `Drive_Dwin.c` 第170-198行，`DWIN_SetMode` 用 switch-case 处理 3 个模式，每组 4 行代码，结构完全相同。

**方案**: 用 VP 地址数组 + 循环简化：
```c
static const u16 VP_MODE_I[3] = {DWIN_VP_MODE_I1, DWIN_VP_MODE_I2, DWIN_VP_MODE_I3};
static const u16 VP_MODE_T[3] = {DWIN_VP_MODE_T1, DWIN_VP_MODE_T2, DWIN_VP_MODE_T3};

void DWIN_SetMode(u8 item)
{
    u8 i;
    if (item > 2) item = 0;
    for (i = 0; i < 3; i++) {
        u8 ico = (i == item) ? DWIN_ICON_SEL : DWIN_ICON_UNSEL;
        const char *txt = (i == item) ? MODE_TXT_SEL[i] : MODE_TXT_UNSEL[i];
        DWIN_WriteU16(VP_MODE_I[i], (u16)ico);
        DWIN_WriteText(VP_MODE_T[i], txt, 12);
    }
}
```

### 4.4 DWIN_SyncParams fref 发送去重

**问题**: `Drive_Dwin.c` 第224-231行，fref 的 u32 发送单独写了一段大端编码代码，和 `DWIN_WriteS32` 完全相同。

**方案**: 直接调用 `DWIN_WriteS32(DWIN_VP_FREF, (s32)v_fref);`，删除重复代码。

## 5. 鲁棒性改进 (P2)

### 5.1 GTI_FullFir 数组越界

**问题**: `GTI_FullFir()` 第606行：
```c
acc += g_fir[k] * (float)raw[m + (GTI_FIR_TAPS - 1) / 2 - k];
```
当 `m < 63`（即 `(FIR_TAPS-1)/2 = 63`）且 `k > m` 时，索引为负数，访问 `raw` 前面的内存。

**方案**: 
- 方案A: 调用处保证 `m >= 63`（当前 `GTI_FIR_OFF + GTI_DECIM * zc + i` 中，`GTI_FIR_OFF=132`，所以 `m >= 132`，实际不会越界。但这依赖于调用者的隐含约束，不安全）。
- 方案B: 在 `GTI_FullFir` 内部加边界检查。
- 方案C（推荐）: 按本文 1.3 节方案，直接用 `g_x[]` 替代 `GTI_FullFir`，彻底消除这个函数。

### 5.2 sprintf 缓冲溢出风险

**问题**: `GTI_ShowSpec()` 第870行：
```c
char s[24];
sprintf(s, "%.0fk", (G.fs / 2.0f * (float)i / 4.0f) / 1000.0f);
```
如果 `G.fs` 异常（如 0 或极大值），格式化结果可能超过 24 字节。

**方案**: 改用 `snprintf`：
```c
snprintf(s, sizeof(s), "%.0fk", (G.fs / 2.0f * (float)i / 4.0f) / 1000.0f);
```

### 5.3 AD9240_Capture 中的延时优化

**问题**: `Drive_AD9240.c` 第212-221行，DMA 完成等待用 `delay_ms(1)` 轮询，每次轮询间隔 1ms。对于高频采样（如 4.8MHz 采 16528 点 ≈ 3.4ms），实际只需等 3.4ms，但轮询可能多等 1ms（取整误差）。

**方案**: 对短采集（<10ms）改用忙等待 + 超时：
```c
if (timeout_ms < 10) {
    // 短采集: 忙等待，不用 delay_ms
    u32 tick_start = Get_Tick();
    while (DMA_GetFlagStatus(...) == RESET) {
        if ((Get_Tick() - tick_start) > timeout_ms) {
            AD9240_Stop();
            return (u16 *)0;
        }
    }
} else {
    // 长采集: delay_ms 轮询（省 CPU）
    // ... 原逻辑
}
```

**收益**: 短采集场景减少 1-2ms 延迟。

### 5.4 DMA 缓冲与 CCM 对齐

**问题**: `s_ad9240_buf` 在主 SRAM 中，DMA 可以访问。但如果编译器把 `s_ad9240_buf` 放到了非 DMA 可达的区域（如 CCM），会导致 DMA 静默失败。

**当前状态**: `s_ad9240_buf` 是 `static` 变量，没有 `__attribute__((section(...)))`，编译器默认放主 SRAM，DMA 可达。安全。

**建议**: 显式标注 section 防止误改：
```c
__attribute__((section(".sram_dma")))
static u16 s_ad9240_buf[AD9240_BUF_SIZE];
```

### 5.5 比较器 g_tim1_overflow 未使用

**问题**: `Drive_Comparator.c` 第56行 `g_tim1_overflow` 在中断中累加，但 `Get_Frequency()` 没有使用它。如果信号频率 > 655.36kHz（闸门 100ms 内 > 65536 个周期），TIM1 的 16 位计数器溢出，`g_signal_count` 会少算。

**当前状态**: 题目最高 500kHz，闸门 100ms 内最多 50,000 个周期，不会溢出。

**建议**: 在 `TIM2_IRQHandler` 中，闸门结束时把 `g_tim1_overflow` 也计入 `g_signal_count`：
```c
// TIM2_IRQHandler 中闸门结束时:
g_signal_count = g_tim1_overflow * 65536 + TIM_GetCapture1(TIM1);
```

## 6. 迪文屏驱动改进 (P2)

### 6.1 DWIN_WriteText 循环变量溢出

**问题**: `Drive_Dwin.c` 第148行 `u8 i` 作为循环变量，如果 `max_len > 255` 会溢出。虽然当前最大 `max_len = 20`，但这是隐患。

**方案**: 改为 `u16 i`。

### 6.2 DWIN_SendWavePoints 分包发送

**问题**: 见 2.3 节，单帧 120 点限制。

**方案**: 实现分包发送，见 2.3 节方案B。

### 6.3 DWIN_SendSpecBars 先清屏再画 → 闪烁

**问题**: `Drive_Dwin.c` 第357行，`DWIN_SendSpecBars` 内部先调用 `DWIN_ClearGraph` 清屏，再发送柱状图数据。清屏和画图之间有一小段空白时间，可能导致闪烁。

**方案**: 取消内部清屏，由调用方在合适时机清屏：
```c
// DWIN_SendSpecBars 内部删除 DWIN_ClearGraph 调用
// 调用方在 GTI_ShowSpec 中:
DWIN_ClearGraph(DWIN_VP_GRAPH_SPEC);
DWIN_SendSpecBars(bar_heights, 30, 15, 3);
```

### 6.4 迪文屏发送阻塞 → 超时保护

**问题**: `Drive_Dwin.c` 第37行 `_tx_byte` 是死循环等待 TXE 标志：
```c
while ((USART1->SR & 0x40) == 0);
```
如果迪文屏未接或 USART 故障，这里会死锁整个系统。

**方案**: 加超时退出：
```c
static void _tx_byte(u8 b)
{
    u32 timeout = 100000;  // 约 0.6ms @168MHz
    while ((USART1->SR & 0x40) == 0) {
        if (--timeout == 0) return;  // 超时放弃
    }
    USART1->DR = b;
}
```

### 7.1 GBK 硬编码字符串 → 注释化

**问题**: `app_gti.c` 中大量 GBK 十六进制中文字符串，如：

```c
#define TXT_AUTO_REFRESH "\xd7\xd4\xb6\xaf\xcb\xa2\xd0\xc2" // 自动刷新
#define TXT_MANUAL_MODE  "\xca\xd6\xb6\xaf\xc4\xa3\xca\xbd" // 手动模式
#define TXT_SELFTEST     "\xd7\xd4\xbc\xec\xc4\xa3\xca\xbd" // 自检模式
#define TXT_REALTIME     "\xca\xb5\xca\xb1\xc4\xa3\xca\xbd" // 实时模式
// ... 使用时:
OS_String_Show(..., TXT_NO_SIGNAL "  ");
```

### 7.2 Drive_Comparator.c/h 中文注释乱码

**问题**: `Drive_Comparator.c` 和 `.h` 的中文注释全部是乱码（UTF-8 被当 GBK 解码），如：

```c
*   function   : 绛夌簿搴﹂?戠巼娴嬮噺 (TLV3501 鏁村舰 -> TIM1 杈撳叆鎹曡幏 PA8)
```

### 7.4 魔法数字消除

**问题**: 多处硬编码数字没有解释：
- `app_gti.c:262` `i < GTI_NBIN - 3` — 为什么是 3？应注释 `/* 跳过 DC 附近 3 bin + 边界 3 bin */`

## 9. 内存预算分析

### 当前 CCM 占用 (约 57KB / 64KB)

| 变量 | 大小 | 说明 |
|------|------|------|
| G (GTI_State) | ~200B | 运行状态 |
| g_x[4096] | 16KB | 分析信号 |
| g_xin[4096] | 16KB | 加窗 FFT 输入 |
| g_xout[4096] | 16KB | FFT 输出 |
| g_mag[2048] | 8KB | 幅度谱 |
| g_fir[127] | 508B | FIR 系数 |
| g_rfft | ~256B | RFFT 实例 |
| g_raw3* | ~8B | 指针+均值 |
| **合计** | **~57KB** | |

### 优化后 CCM 占用 (约 49KB / 64KB)

| 变量 | 大小 | 变化 |
|------|------|------|
| G | ~200B | 不变 |
| g_x[4096] | 16KB | 不变 |
| g_fft[4096] | 16KB | g_xin+g_xout 合并，**省 16KB** |
| g_hann[4096] | 16KB | **新增** 窗表 |
| g_mag[2048] | 8KB | 不变 |
| g_fir[127] | 508B | 不变 |
| g_rfft | ~256B | 不变 |
| g_fir_dec | ~100B | **新增** CMSIS-DSP 实例 |
| g_fir_state | ~66KB | **问题**: 放不下 CCM |
| **合计** | **~49KB** (不含 g_fir_state) |

**g_fir_state 问题**: `arm_fir_decimate_f32` 的状态缓冲需要 `block_size + num_taps - 1 = 16528 + 126 = 16654` 个 float = 66.6KB，CCM 放不下。

**解决方案**:
- g_fir_state 放主 SRAM（DMA 不用这块数据，CPU 专用即可）
- 或者不使用 CMSIS-DSP 的 FIR，保持手动实现但优化循环（见 1.2 节备选方案）

### 主 SRAM 占用

| 变量 | 大小 | 说明 |
|------|------|------|
| s_ad9240_buf | 32.3KB | DMA 采集缓冲 |
| g_fir_state | 66.6KB | **新增** CMSIS-DSP FIR 状态（如果用） |
| 旧代码变量 | ~20KB | 估算 |
| 栈/堆 | ~4KB | |
| **合计** | **~123KB** (含 g_fir_state) | 128KB SRAM，紧张 |

**结论**: 如果用 CMSIS-DSP FIR，g_fir_state 必须放 CCM 外。但 CCM 也放不下。备选方案：保持手动 FIR 但用 `arm_fir_f32`（不抽取），分块处理。或者直接保持当前手动实现，只做 1.3 的优化（消除 GTI_FullFir 重复计算），CMSIS-DSP 替换作为可选优化。
