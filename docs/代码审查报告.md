## 二、🔴 致命问题 (Fatal)

---

### F1. main.c:72 — 语法错误：多余字符`5`

**文件**: `BSP/main.c`，第72行

**问题**:
```c
int main(void)
5{          // <-- '5' 多余，编译必定失败
    uint16_t key;
```

**影响**: AC6编译器报错 `error: expected '{'`，**项目无法编译**。  
**修正**: 删除第72行的`5`字符，改为纯`{`。

---

### F2. PC0/PC2/PC3 — AD9959引脚与SDRAM芯片直接硬件冲突

**文件**: `BSP/config.h` 第74-78行, `BSP/Drive_AD9959.c`  
**参考**: 阿波罗V2 IO引脚分配表（底板原理图V2.5）

| 项目引脚 | 功能 | 开发板实际连接 | 是否引出到排针 |
|----------|------|---------------|:---:|
| **PC0** | DDS SCLK | `FMC_SDNWE` (SDRAM WE, W9825G6KH) | ❌ |
| **PC2** | DDS CS | `FMC_SDNE0` (SDRAM CS, W9825G6KH) | ❌ |
| **PC3** | DDS IO_UPDATE | `FMC_SDCKE0` (SDRAM CKE, W9825G6KH) | ❌ |

**问题分析**:
- 这三个引脚**直接PCB走线连接到SDRAM芯片**，手册标注"未引出，不能做普通IO用"
- 即使FMC未初始化，GPIO推挽输出的电平变化仍直接施加到SDRAM引脚
- **PC2 (SDRAM CS) 最为危险**: GPIO输出低电平时意外使能SDRAM芯片，可能导致总线冲突

**修正**: **必须更换引脚**。建议候选（需逐一确认不与板载外设冲突）:
- PA4/PA5/PA6/PA7, PB0/PB1/PB3/PB4/PB5, PD8-PD15

---

### F3. PE0-PE6 — AD9240 D0-D6 与SDRAM/ES8388音频芯片冲突

**文件**: `BSP/Drive_AD9240.c` 第23-26行, `BSP/config.h` 第57行

| 引脚 | ADC功能 | 开发板实际连接 | 风险 |
|------|---------|---------------|------|
| PE0 | D0 | FMC_NBL0 (SDRAM字节掩码) | 🔴 SDRAM专用 |
| PE1 | D1 | FMC_NBL1 (SDRAM字节掩码) | 🔴 SDRAM专用 |
| PE2 | D2 | SAI1_MCLKA (ES8388音频主时钟) | 🔴 音频芯片可能输出信号 |
| PE3 | D3 | SAI1_SDB (ES8388音频数据输出) | 🔴 音频芯片可能输出信号 |
| PE4 | D4 | SAI1_FSA (ES8388帧同步) | 🔴 音频芯片可能输出信号 |
| PE5 | D5 | SAI1_SCKA (ES8388位时钟) | 🔴 音频芯片可能输出信号 |
| PE6 | D6 | SAI1_SDA (ES8388数据输入) | 🔴 音频芯片可能输出信号 |

**问题分析**:
- 项目注释称"不初始化FMC, SDRAM高阻不干扰"——这对PE7-PE13勉强成立，但：
  - PE0-PE1是SDRAM **控制信号**（NBL），非数据线，不适用"高阻"假设
  - PE2-PE6连接**ES8388音频芯片**，该芯片上电后MCLK/SCLK/LRCK等引脚可能主动输出信号，与ADC输入电平冲突

**修正**:
- 方案A（推荐）: 将ADC数据总线全部换到其他空闲16位端口
- 方案B: 如必须用PE，至少断开ES8388供电或将ES8388复位引脚拉低

---

### F4. link.sct — CCM段可能导致DMA传输失败

**文件**: `link.sct`

**问题**:
```c
RW_IRAM2 0x10000000 0x00010000  {
    .ANY (+RW +ZI)         // ← 可能把DMA缓冲分配到CCM!
}
```
- CCM (0x10000000) 只能CPU访问，**DMA无法访问CCM**
- `ad9240_buf[16384]` (32KB) 是DMA目标缓冲，如果链接器将它放入CCM，DMA将静默失败
- 当前 link.sct 允许任意RW/ZI数据进入CCM，存在风险

**修正**: 改为仅放置明确标记的段：
```c
RW_IRAM2 0x10000000 0x00010000  {
    *(.ccm_ram)
}
```
或在 `Drive_AD9240.c` 中给DMA缓冲标记非CCM段：
```c
__attribute__((section(".dma_ram"))) volatile uint16_t ad9240_buf[MAX_ADC_BUF_SIZE];
```

## 三、🟡 警告 (Warning)

---

### W1. 时钟树双重配置 — system_stm32f4xx.c 与 main.c 不一致

**文件**: `_02_Core/system_stm32f4xx.c` 第325行, `BSP/main.c` 第39行

| 参数 | SystemInit()→SetSysClock() | main.c→RCC_Config() |
|------|:---:|:---:|
| PLL_N | **360** | **336** |
| SYSCLK | **180MHz** | **168MHz** |
| APB1 | 45MHz | 42MHz |
| APB2 | 90MHz | 84MHz |

**问题**: 上电后路径: HSI→HSE→180MHz→HSI→HSE→168MHz，多余时钟切换。如果未来有人移除RCC_Config()（如改用HAL），系统将跑在180MHz但所有定时器/波特率参数按168MHz计算。  
**修正**: 修改 system_stm32f4xx.c 中 `PLL_N` 从360改为336，与main.c统一。

---

### W2. RCC_Config() 缺少 F429 Over-Drive 模式

**文件**: `BSP/main.c` 第25-52行  
**参考**: 阿波罗官方 system_stm32f4xx.c SetSysClock()

**问题**: SystemInit()临时进入180MHz时设置了Over-Drive，但RCC_DeInit()会清除。RCC_Config()配168MHz时没有重建。STM32F429在高频运行时需要Over-Drive。  
**修正**: 在FLASH_ACR设置之前添加:
```c
if ((PWR->CSR & PWR_CSR_ODSWRDY) == 0) {
    PWR->CR |= PWR_CR_ODEN;
    while ((PWR->CSR & PWR_CSR_ODSWRDY) == 0);
}
PWR->CR |= PWR_CR_ODSWEN;
while ((PWR->CSR & PWR_CSR_ODSWRDY) == 0);
```

---

### W3. PWR VOS 未等待就绪标志

**文件**: `BSP/main.c` 第33行  
**问题**:
```c
PWR->CR |= PWR_CR_VOS;   // 设置Scale1，但没等VOSRDY!
```
**修正**: 添加等待:
```c
PWR->CR |= PWR_CR_VOS;
while ((PWR->CSR & PWR_CSR_VOSRDY) == 0);
```

---

### W4. delay_us() 精度极差 — 裸NOP循环

**文件**: `BSP/delay.c` 第11-14行  
**参考**: 正点原子官方delay.c (V1.0, 2022, 使用SysTick精确定时)

**问题**:
```c
void delay_us(uint32_t us) {
    uint32_t ticks = us * 21;  // 168MHz/8=21MHz
    while (ticks--) __NOP();   // 每个NOP并非精确1周期!
}
```
- Flash 5WS等待周期显著影响NOP执行时间
- 中断抢占进一步扭曲
- 20us短延时实测误差可能超50%
- 正点原子官方版使用SysTick->VAL硬件定时，精度远高于此

**修正**: 替换为正点原子官方SysTick微秒延时实现。

---

### W5. ADC DMA缓冲无内存对齐声明

**文件**: `BSP/Drive_AD9240.c` 第17行  
**问题**:
```c
volatile uint16_t ad9240_buf[MAX_ADC_BUF_SIZE];  // 无对齐
```
DMA传输对内存对齐敏感。  
**修正**:
```c
volatile uint16_t ad9240_buf[MAX_ADC_BUF_SIZE] __attribute__((aligned(16)));
```

---

### W6. DMA超时循环无错误标志检查

**文件**: `BSP/Drive_AD9240.c` 第65-72行  
**问题**: 仅检查TC标志，不检查TEIF(传输错误)和FEIF(FIFO错误)。DMA可能因配置错误永久失败。  
**修正**: 增加 `DMA_GetFlagStatus(..., DMA_FLAG_TEIF1|DMA_FLAG_FEIF1)` 检查。

---

### W7. Hanning窗重复定义 — 浪费16KB SRAM

**文件**: `BSP/app_fft.c` 第20行, `BSP/app_measure.c` 第40行  
**问题**: 两个文件各自定义了独立的 `static float g_hanning[4096]`（各16KB），功能完全相同。浪费16KB SRAM（当前使用约150KB/192KB）。  
**修正**: 删除app_measure.c中的g_hanning，统一使用app_fft.c中的版本。

---

### W8. Dwin_ReadKey() 无帧长度验证

**文件**: `BSP/Drive_Dwin.c` 第123-137行  
**问题**: 访问 `g_rx_buf[6-8]` 前未验证 `g_rx_len >= 9`。若收到其他0x83帧（如读VP应答只有8字节），会越界读取。  
**修正**: 
```c
if (g_rx_expect >= 9 && g_rx_buf[3] == 0x83 && ...
```

---

### W9. 所有异常处理函数都是死循环

**文件**: `BSP/stm32f4xx_it.c` 第7-10行, `BSP/main.c` 第96-99行  
**问题**: NMI/MemManage/BusFault/UsageFault/HardFault 全部是 `while(1);`，无任何状态保存。发生异常时CFSR/HFSR/PC/LR全部丢失，无法定位。  
**修正**: 至少保存关键寄存器到全局变量供调试器查看。

---

### W10. 比较器测频闸门时间不准

**文件**: `BSP/Drive_Comparator.c` 第72-75行  
**问题**: 
```c
for (i = 0; i < 100; i++) delay_us(1000);  /* 100ms 不准确 */
```
结合W4的delay精度问题，100ms闸门实际可能有±2%以上的误差，直接导致频率测量误差。  
**修正**: 使用TIM1自身的定时功能精确定时。

---

### W11. app_fft.h 平台名称错误

**文件**: `BSP/app_fft.h` 第3行  
**问题**: `* 平台: STM32F407ZG` 实际为 **STM32F429IGT6**。  
**修正**: 更正为 STM32F429IGT6。

---

### W12. Drive_Dwin.h 波特率注释与config.h不一致

**文件**: `BSP/Drive_Dwin.h` 第2-3行, `BSP/config.h`  
**问题**: 头文件注释写 `(当前921600)`，但config.h定义DWIN_BAUD=115200。误导性注释。  
**修正**: 删除括号内具体数值或使用宏引用。

---

### W13. PA8 — 比较器输入与LF0038红外接收头共引脚

**文件**: `BSP/Drive_Comparator.c`  
**参考**: 阿波罗V2 IO引脚分配表

**问题**: PA8同时连接LF0038红外接收头（REMOTE_IN, 4.7K上拉）和DCMI_XCLK（摄像头）。TLV3501推挽输出足以驱动，但红外接收头的空闲输出可能干扰。  
**修正**: 确认红外接收头处于断电/禁用状态。

---

### W14. PC1/PC4 — 以太网PHY引脚依赖复位状态

**文件**: `BSP/Drive_AD9959.c`, `BSP/config.h`  
**参考**: 阿波罗V2 IO引脚分配表

| 引脚 | DDS功能 | 开发板连接 | 安全条件 |
|------|---------|-----------|----------|
| PC1 | SDATA | ETH_MDC (YT8512C) | 需PHY保持复位 |
| PC4 | RESET | ETH_RXD0 (YT8512C) | 需PHY保持复位 |

**问题**: 代码中没有任何确保YT8512C以太网PHY处于复位的操作。PHY上电后若脱离复位状态会驱动这些引脚。  
**修正**: 在初始化中显式复位以太网PHY。

---

### W15. Measure_Run()波形模式缺少错误检查

**文件**: `BSP/app_measure.c`  
**问题**: AD9240_Start()返回值未检查，若返回-1（参数错误）仍继续执行后续逻辑。  
**修正**: 增加返回值检查，失败时跳过本次测量。

---

### W16. 测试文件混入正式工程

**文件**: `BSP/test_apollo.c`, `test_pb6_high.c`, `test_pin.c`, `test_screen.c`, `test_simple.c`, `test_uart_diag.c` (共6个)  
**问题**: BSP目录下有6个测试/诊断文件，不属于正式工程（.uvprojx中也未包含）。这些文件可能包含过时的引脚配置，容易混淆。  
**修正**: 移到单独的 `BSP/tests/` 目录或删除。

## 四、🟢 建议 (Suggestion)

---

### S1. 库版本过旧

**当前**: STM32F4xx StdPeriph Lib V1.4.0 (2014)  
**参考**: 正点原子官方 HAL Driver (2017+)  

ST已停止维护StdPeriph库。考虑到比赛时间紧迫可暂不改动，但长期建议迁移到HAL。

---

### S2. 编译器兼容性 — AC6 vs ARMCC V5

**文件**: `电赛.uvprojx`  
**问题**: 项目用ARMCLANG V6.22 (AC6)，正点原子官方用ARMCC V5。CMSIS-DSP的 `arm_cortexM4lf_math.lib` 是V5格式，AC6下需验证兼容性。  
**修正**: 验证DSP库链接正常；如有问题，换用AC6版本或源码编译。

---

### S3. 开启 USE_FULL_ASSERT

**文件**: `_02_Core/stm32f4xx_conf.h`  
**问题**: 调试阶段建议取消注释 `#define USE_FULL_ASSERT`，让库函数参数检查生效。

---

### S4. 寄存器直接操作不够规范

**文件**: `BSP/Drive_AD9240.c` 第34行  
**问题**:
```c
RCC->AHB3ENR &= ~0x00000001;  // 魔数+绕开API
```
**修正**:
```c
RCC_AHB3PeriphClockCmd(RCC_AHB3Periph_FMC, DISABLE);
```

---

### S5. DGUS大帧发送缺少流控

**文件**: `BSP/Drive_Dwin.c` Dwin_DrawWave/Dwin_DrawSpectrum  
**问题**: 每帧242字节@115200bps ≈ 21ms，连续分包时可能在UART发送缓冲区满时丢数据。  
**修正**: 每帧发送后等待TXE+TC标志，或使用DMA发送。

---

### S6. 缺少统一版本号

所有BSP源文件没有版本号和修改日志。建议参考正点原子格式 `@version V1.0 @date 2026-07-31`。

---

### S7. DGUS通信无超时看门狗

Dwin_ReadKey()依赖 `g_rx_ready` 标志，若USART1硬件故障则永不返回。建议添加超时复位。

---

### S8. DWIN_BAUD宏未在Drive_Dwin.c中使用

**文件**: `BSP/Drive_Dwin.c` 第32行  
**问题**: USART1波特率硬编码 `USART_InitStructure.USART_BaudRate = 115200;`，而不是引用config.h中的 `DWIN_BAUD` 宏。如果以后需要改波特率，需要改两处。  
**修正**: 使用 `DWIN_BAUD` 宏。
